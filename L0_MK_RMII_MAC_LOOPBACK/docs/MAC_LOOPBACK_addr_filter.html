Receive-side MAC address filter: mode 11 case by case

Cheat sheet for eth_run_test_ops = 11 (eth_mac_addr_filter_lb, file eth_addr_functions.c). STM32H755, RM0399 Rev 4. Mode 11 has not run on the board yet. Mode 1 (eth_filter_functions.c, 24 cases) ran on 2026-10-16 with 24/24, so many of the predictions below are things the board has already told us; section 9 says clearly what is already known and what is still pending.

Mnemonic: With PR off, the MAC only accepts a frame whose DA matches one of the four slots MACA0..3 (or hits a hash bit, or is an allowed broadcast / multicast). Slots 1..3 can also be turned off (AE), compare the sender instead of the receiver (SA), and mask bytes (MBC). A miss means the frame is lost, with no descriptor.

1. What mode 11 tests

In mode 0 and modes 2..10, mac_basic_init writes ETH_MACPFR.PR = 1: the address filter is bypassed and the MAC accepts every DA. That is why test frames with DA 6C:1F:F7:CA:2B:FD (not the board's address) still come back. A real driver does not run like that. Mode 11 keeps PR = 0 for the whole test and asks three questions: who gets in, who gets dropped, and what the descriptor says about why.

The address filter is the first layer in the filter chain (figure 830 p.2954): address → VLAN (mode 8) → L3/L4. A frame that misses at this layer never reaches the VLAN filter (p.2957).

Mode 1 (eth_run_test_ops = 1, eth_filter_functions.c) is the earlier address-filter test, in the style of a 24-row CASES[] table, each row one 22-byte frame. The board ran it on 2026-10-16 (log COM3_2026_10_16): 24/24. What it proved, and mode 11 no longer needs to doubt:

2. The four address slots MACA0..3

The x in ETH_MACAxHR is the slot number inside one MAC, not a port number. The H755 has one port and four slots. Each slot is a pair of registers because 48 bits do not fit in 32:

When to use which slot: MACA0 = your own address (DA filtering, SA of pause frames, source for SARC/SAIC). MACA1..3 = exceptions: a second unicast address (E), a group sharing an OUI via MBC (G), one specific multicast group without needing PM (I), accept only from one sender via SA + SAF (L). Write order: LR first, HR after. HR holds AE, so writing HR last means the address is complete before the slot is enabled. p.3154 also says synchronisation into the MII clock domain is triggered by writing byte [31:24] of LR. af_case writes LR, then HR.

4. The 64-bit hash table (ETH_MACHT0R / 1R, p.3121)

When the number of addresses to accept exceeds the 4 slots (IPv4/IPv6 multicast, many virtual addresses), the MAC filters "approximately" with a 64-bit table:

  1. CRC-32 of the 6 DA bytes (IEEE 802.3, like the FCS): reflected, initialised to 0xFFFFFFFF, bit 0 of byte 0 first.
  2. Take the complement (~), reverse the 32 bits.
  3. The top 6 bits = index 0..63. Bit 5 selects HT1R (32..63) or HT0R (0..31), bits 4:0 select the bit in the register.
  4. If that bit = 1, the frame passes. Many addresses can land on the same bit: "imperfect filtering", software has to filter again.
af_hash_index():  MACA0 00:80:E1:00:00:00 → 13 (HT0R bit 13)    02:00:00:00:00:99 → 4 (HT0R bit 4)
                  02:11:22:33:44:55 → 14                        01:00:5E:01:02:03 → 6
K1 writes ETH_MACHT0R = 1 << 4 = 0x00000010
The formula is copied from the Linux driver (bitrev32(~crc32_le(~0, addr, 6)) >> 26) and the board confirmed it in mode 1 (2026-10-16): five frames passed through the hash with RDES2.HF = 1 and MADRM exactly equal to the index the software computed (mDNS 48, all-hosts 32, 01:00:5E:00:00:18 → 32, 01:00:5E:00:00:C9 → 48, 6C:1F:F7:CA:2B:FD → 34). Mode 8 case H uses the same CRC for the VLAN hash. RM p.3121 says "take the upper 7 or 8 bits" (generic across table sizes); for a 64-bit table it is 6 bits. Mode 1's two addresses ..:18 and ..:C9 deliberately collide on a bit with all-hosts / mDNS and still pass: "imperfect filtering" is real, and software has to filter again.
