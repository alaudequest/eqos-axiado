Checksum offload: the MAC computes and checks IP/TCP/UDP checksums, mode 7 case by case

Cheat sheet for eth_run_test_ops = 7 (eth_mac_coe_lb, file eth_coe_functions.c). STM32H755, RM0399 Rev 4, COE §61.5.5 p.2985-2990. Run on the board 3 times (2026-11-08 6/7, 11-09 8/8, 11-10 8/8); section 8 records two lessons the board and the code taught.

Mnemonic: Transmitter: TDES3.CIC tells the MAC which checksum to insert (00 none, 01 IP, 10 IP + TCP/UDP with the pseudo sum provided by the CPU, 11 the MAC does everything). Receiver: with ETH_MACCR.IPC = 1 the MAC recomputes both and writes the result into RDES1 (IPHE bad header, IPCE bad payload, PT payload type). A bad frame only reaches RAM when DIS_TCP_EF = 1.

1. What mode 7 tests

A TCP/IP stack has to compute two checksums for every outgoing frame: one over the IP header (20 bytes) and one over TCP/UDP (header + payload + a "pseudo header" built from the IP addresses). On a 400 MHz CPU this costs a few microseconds per frame; the MAC has a built-in block that does it instead, called the Checksum Offload Engine (COE). Mode 7 asks three questions: (1) does the transmitter insert the right checksum according to TDES3.CIC, (2) does the receiver correctly detect a bad checksum, (3) do the software and the MAC compute it the same way.

How it is tested: the same 154-byte TCP/IP frame (G: 142-byte UDP) for every case; only the two checksum fields and CIC change. The frame goes through loopback back to RX. The software re-checks the checksums on the received frame (RFC 1071), then compares with what RDES1 says. Each case has two independent witnesses; it is BAD when either of them is not as expected.

In the other modes the frame uses the "experimental" EtherType 0x88B5, so the COE leaves it alone. Mode 7 is the first mode that sends a real IPv4 frame (EtherType 0x0800) with standard-conforming IP and TCP headers; otherwise the COE skips it (RDES1.IPCB = 1, "bypassed").

2. The test frame and the pseudo header

Built in co_build(), bytes big-endian. The two fields in square brackets are the two checksum fields that co_set_csums() fills in per case: 0, the correct value, or (L4 only) the pseudo header sum.

Correct values for this frame (computed by software, reused in section 7): IP csum = 73 DC (TCP) / 73 DD (UDP); TCP csum = C3 9B; UDP csum = 43 49; fold(TCP pseudo header) = 83 ED. The first four values match the "frame received" lines in the 2026-11-09 log exactly.

Why there is a pseudo header (RFC 793 for TCP, RFC 768 for UDP): the L4 checksum also covers the source/destination IP addresses and the protocol, even though they are not inside the TCP segment. That way a frame that a router delivers to the wrong machine also has a bad TCP checksum. Consequence for the MAC: to compute the TCP checksum it must read the IP header first, so the COE only runs when the frame is a well-formed IPv4/IPv6 frame (p.2986).

Why CIC = 10 wants the sum uncomplemented: the real checksum = ~fold(sum). With CIC = 10 the MAC does not build the pseudo header itself (p.2987); it takes the value in the checksum field as the starting sum, adds header + payload, folds, and only then complements once. If the CPU writes ~fold(pseudo) there, the MAC adds an already-complemented sum and the result is wrong. Code: CO_SEND_PSEUDO writes csum_fold(csum_pseudo(...)) without the ~.

Limit, p.2986: the transmitter must hold the whole frame in the TX FIFO before transmitting (store-and-forward) so it knows the sum before the checksum bytes go onto the wire. A frame with CIC ≠ 00 must be smaller than TQS − (PBL + 7) × 4 = 2048 − 60 bytes with this configuration; a 154-byte frame is far below that. For a longer frame the MAC does not insert and reports TDES3.PCE = 1.

3. TDES3.CIC: four choices at the transmitter (p.3052)

CIC [17:16]Name in the codeMAC insertsCPU must doCase
00TDES3_CIC_NONEnothing, the frame goes out as iscompute both itself (or send them wrong to test RX)A B C H
01TDES3_CIC_IPIP header checksum [24..25]compute TCP/UDP itselfD
10TDES3_CIC_IP_PAYLOADIP + TCP/UDP, but the pseudo header sum is supplied by the CPUwrite the uncomplemented fold(pseudo) into the L4 fieldF
11TDES3_CIC_FULLIP + TCP/UDP, the MAC builds the pseudo header itselfleave both fields = 0E G (and TSO mode 6 forces it)

Only takes effect on the frame's first descriptor (FD = 1) and for IPv4/IPv6 frames. egress_packet() copies the global variable eth_tx_cic into TDES3 [17:16] on every send; at the end of the test it is reset to 0 so other modes do not get unwanted insertion.

What the transmitter reports back (TDES3 write-back, p.3055): IHE [0] = 1 "IP header error": the MAC was asked to insert but the IP header is invalid (not 0800/86DD, unusual IHL, total length larger than the frame). PCE [12] = 1 "payload checksum error": the L4 checksum could not be inserted (protocol not TCP/UDP/ICMP, frame over the store-and-forward limit). In mode 7 both must be 0 in every case with CIC ≠ 00; with CIC = 00 these two bits mean nothing.

4. ETH_MACCR.IPC and RDES1 at the receiver

Set one bit: ETH_MACCR.IPC [27] = 1 (p.3112), written before RE = 1. From then on, for every IPv4/IPv6 frame the MAC recomputes the header checksum and the L4 checksum and writes the result into RDES1 of the receive descriptor (p.3066), only meaningful when RDES3.RS1V [26] = 1. The MAC does not modify the frame on receive; it only reports.

RDES1 bitNameMeaningMode 7 expects
[2:0]PT, payload type0 not processed / 1 UDP / 2 TCP / 3 ICMP / 4..7 reserved (IPv6 extension...)2 TCP, 1 UDP (G); even when IPHE = 1, board 11-08
[3]IPHE, IP header errorIP header checksum wrong, or version / IHL / length mismatch1 in A, H
[4]IPV4the frame is IPv4 (EtherType 0800)1 in every case
[5]IPV6the frame is IPv60
[6]IPCB, checksum bypassedthe COE did not check it (not IP, fragment, IPC = 0...)0
[7]IPCE, payload checksum errorTCP/UDP/ICMP checksum wrong1 in B, D, H

Why a bad frame still reaches RAM: the MTL has a switch, ETH_MTLRXQOMR.DIS_TCP_EF [6] (p.3106). = 0 (reset): a frame with IPCE / IPHE is dropped by the MTL, no descriptor, software only sees a counter go up. init_mac_internal_lb() sets it to 1 so the test can see RDES1 of the bad frame. A real driver usually leaves it at 0 to save work.

Does the core have COE: ETH_MACHWF0R (p.3142) TXCOESEL [14] and RXCOESEL [16] read 1 on the H755; the code checks first and stops the test if they are missing (in case of porting to another core).

7. Eight cases, one at a time

Every case: ETH_MACCR.IPC = 1, DIS_TCP_EF = 1, the same 154-byte TCP frame (G: 142-byte UDP). "What the board says" comes from the 2026-11-08 / 09 / 10 logs in CM7/Core/Src/log.

A: CIC 00, IP csum = 0, TCP correct deliberate error

TDES3.CIC00: no insertion
CPU writes into the frameIP csum [24..25] = 00 00 (wrong), TCP csum = C3 9B (computed correctly by the CPU)
What the MAC does on transmitLeaves the frame alone, sends it as is.
On the wire (software check, RFC 1071)ip BAD, l4 ok. The frame comes back identical to what was sent.
Expected RDES1IPV4 = 1, IPHE = 1, PT = 2, IPCE = 0: the header is bad but the MAC still checks TCP.
What the board says2026-11-08: BAD because the code expected PT = 0 (from reading p.3067). Board: PT = 2, IPCE = 0 → expectation fixed. 11-09, 11-10: OK.
Watch forThe p.3067 sentence "PT = 0 when the COE does not process the payload because of an IP header error" is about the header structure errors on p.2986 (version, IHL, frame shorter than total length), not about a wrong checksum. The most expensive lesson of this mode.

B: CIC 00, IP correct, TCP csum = 0 deliberate error

TDES3.CIC00: no insertion
CPU writes into the frameIP csum [24..25] = 73 DC (correct), TCP csum = 00 00 (wrong)
What the MAC does on transmitLeaves the frame alone.
On the wire (software check, RFC 1071)ip ok, l4 BAD.
Expected RDES1IPV4 = 1, PT = 2, IPHE = 0, IPCE = 1.
What the board says11-08, 11-09, 11-10: OK. (The test's opening line used to print 'Case B prints FLOW' while the flag was set on D: changed to D on 2026-11-19.)
Watch forIPCE is the only bit that reports a bad payload. The frame still comes up because DIS_TCP_EF = 1 (section 4); a real driver with DIS_TCP_EF = 0 would have the MTL drop this frame outright.

C: CIC 00, the CPU computes both OK

TDES3.CIC00: no insertion
CPU writes into the frameIP csum [24..25] = 73 DC, TCP csum = C3 9B
What the MAC does on transmitLeaves the frame alone.
On the wire (software check, RFC 1071)ip ok, l4 ok.
Expected RDES1IPV4 = 1, PT = 2, IPHE = 0, IPCE = 0, IPCB = 0.
What the board says11-08, 11-09, 11-10: OK.
Watch forThe reference case: the software and the MAC agree on how to compute. If C is BAD, csum_add / csum_pseudo in the code are wrong; do not trust any other case.

D: CIC 01, both = 0: the MAC inserts IP only deliberate error

TDES3.CIC01: IP header checksum
CPU writes into the frameIP csum [24..25] = 00 00, TCP csum = 00 00
What the MAC does on transmitComputes the checksum over the 20-byte IP header and writes it into [24..25]. Leaves TCP alone.
On the wire (software check, RFC 1071)ip ok (MAC wrote 73 DC), l4 BAD.
Expected RDES1IPHE = 0, IPCE = 1, PT = 2. TDES3 write-back IHE = 0.
What the board says11-08, 11-09, 11-10: OK. Case D prints FLOW [10]/[11] in the current code.
Watch forUsed when the stack computes TCP itself (rare) or for frames that are not TCP/UDP. The received frame's bytes 24..25 differ from the sent frame: co_same_but_csums skips exactly the 4 checksum bytes when comparing.

E: CIC 11, both = 0: the MAC inserts everything OK

TDES3.CIC11: IP + payload, the MAC computes the pseudo header itself
CPU writes into the frameIP csum [24..25] = 00 00, TCP csum = 00 00
What the MAC does on transmitComputes both the IP checksum and the TCP checksum, including the pseudo header (taking the source/destination IP, protocol and length from the header itself).
On the wire (software check, RFC 1071)ip ok (73 DC), l4 ok (C3 9B).
Expected RDES1IPHE = 0, IPCE = 0, PT = 2. IHE = PCE = 0.
What the board says11-08, 11-09, 11-10: OK.
Watch forThis is the mode the Linux driver uses for every TCP/UDP frame (and TSO forces it, mode 6). The CPU only has to leave both checksum fields = 0.

F: CIC 10, TCP = pseudo header sum OK

TDES3.CIC10: IP + payload, the CPU provides the pseudo sum
CPU writes into the frameIP csum [24..25] = 00 00, TCP csum = 83 ED = fold(pseudo), NOT complemented
What the MAC does on transmitAdds the TCP header + payload to the value already in the checksum field, takes the one's complement, writes it back. Inserts the IP checksum as in D.
On the wire (software check, RFC 1071)ip ok, l4 ok: the final result is still C3 9B, as in E.
Expected RDES1IPHE = 0, IPCE = 0, PT = 2.
What the board says11-08, 11-09, 11-10: OK.
Watch forIf the CPU mistakenly writes ~fold(pseudo) (the complemented form, like a real checksum), the MAC adds it wrongly and IPCE = 1. Section 2 explains why it must be left uncomplemented.

G: CIC 11 with UDP OK

TDES3.CIC11
CPU writes into the frameIP csum [24..25] = 00 00, UDP csum = 00 00
What the MAC does on transmitLike E but protocol 17: the pseudo header uses UDP length 108, and the checksum goes into [40..41].
On the wire (software check, RFC 1071)ip ok (73 DD), l4 ok (43 49). Frame 142 byte.
Expected RDES1PT = 1 (UDP), IPHE = 0, IPCE = 0.
What the board says11-09: OK, PT = 1. 11-10: prints PT = 2 yet still OK, because the code at that time passed CO_PROTO_TCP for case G (a source bug, found on 2026-11-19 while writing this page, now fixed to CO_PROTO_UDP). Needs a re-run.
Watch forThe expectations in co_case are derived from the proto parameter, so when proto is wrong the expectation is wrong too and the test still says "OK": a test that checks itself against its own inputs cannot catch a wrong function call. Only reading the PT column by eye reveals it.

H: CIC 00, both = 0 deliberate error

TDES3.CIC00: no insertion
CPU writes into the frameIP csum [24..25] = 00 00, TCP csum = 00 00
What the MAC does on transmitLeaves the frame alone.
On the wire (software check, RFC 1071)ip BAD, l4 BAD.
Expected RDES1IPHE = 1 and IPCE = 1, PT = 2.
What the board says11-09, 11-10: OK (case added after 11-08).

8. Lessons from the board

Mode 7 is one of the few modes with three runs; each of the three taught something different.
