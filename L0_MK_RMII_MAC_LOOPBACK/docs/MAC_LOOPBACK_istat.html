Interrupt status with no interrupts enabled: mode 12 case by case

Cheat sheet for eth_run_test_ops = 12 (eth_mac_int_status_lb, file eth_istat_functions.c). STM32H755, RM0399 Rev 4. Written 2026-11-19, not run on the board yet: section 8 is waiting for a log. The test's requirement: no interrupt enabled at all (ETH_DMACIER = 0, ETH_MACIER = 0, the ETH_MTLQICSR enables = 0, NVIC untouched); it only checks whether the status registers reflect events and how they are cleared.

Mnemonic: Status and interrupt are two layers. An event always sets its status bit (TI, RBU, FBE…) even with enable = 0; only AIS / NIS and the NVIC interrupt line need an enable. Clearing status: write 1 (DMA, MTL), read (counters, MAC). A descriptor that does not request IOC produces no TI / RI.

1. What mode 12 tests

The previous eleven modes all poll the descriptor's OWN bit; nobody looks at ETH_DMACSR unless there is an error. A real driver lives on these bits: the ISR reads DMACSR, decides "new frame", "out of descriptors", "bus error", then writes 1 to clear. Before enabling real interrupts, mode 12 asks: does the status bit come up at the right moment, which bit comes up, how is it cleared, and with nothing enabled do AIS / NIS stay quiet. Each case creates one event (a frame, running out of descriptors, FIFO overflow, an oversized frame, a stop command, a bus error) and then reads six registers.

4. The AIS / NIS rule (p.3094)

RM: "Normal Interrupt Summary bit value is the logical OR of the following bits when the corresponding interrupt bits are enabled in the ETH_DMACIER register… Only unmasked bits affect the Normal Interrupt Summary bit." The same sentence exists for AIS. So with DMACIER = 0, TI / RBU / FBE still come up but AIS / NIS = 0.

The board has said it once already: mode 4 case F (2026-11-07) recorded ETH_DMACSR = 0x2C04 = TBU ETI ERI CDE, AIS = 0, with DMACIER = 0. Mode 12 grades "AIS = 0, NIS = 0" in every case to turn a chance observation into a checked rule.

Consequence for the driver: an ISR must not look only at NIS / AIS and conclude "nothing happened" when a bit is not enabled; and clearing must clear both the source bit and the summary bit (both are sticky).

5. IOC and the descriptor the DMA is holding

TI only comes up for a TX descriptor with TDES2.IOC [31] = 1 (p.3050); RI only comes up for an RX descriptor with RDES3.IOC [30] = 1 (p.3064). The code adds two flags, eth_tx_ioc / eth_rx_ioc (like eth_tx_cic), so egress_packet and rx_desc_give_back set that bit.

The trap in case C: after closing a descriptor, the RX DMA immediately prefetches the next one (RPS0 = 3 "waiting for packet" means it is already holding a descriptor). That descriptor was handed back in case B, without IOC. Editing RDES3 in RAM at that point is useless (and the RM forbids modifying a descriptor the DMA is holding). The clean way: send 8 frames so the ring goes all the way round, every descriptor is handed back with IOC, and only then grade the 9th frame.

RX ring (8):   [0 B][1 B][2 B][3 B][4 B][5 B][6 B][7 B]     B = handed back in case B, IOC = 0; the DMA holds [k]
8 warm-up frames → each give-back writes IOC = 1 → [0 C][1 C]…[7 C]
9th frame → descriptor has IOC → RDES3 closed, RI = 1

7. Ten cases

A: After init + start, nothing sent yet status

Setupmac_init_100m → init_mac_internal_lb → mac_start. ETH_DMACIER = 0, ETH_MACIER = 0.
EventNone. Read the 6 registers "as found", then write 1 to every rc_w1 bit of ETH_DMACSR (is_clear).
Expected (DMACSR and more)After clearing: every rc_w1 bit = 0. Before clearing it is only printed: TBU = 1 is normal (once started, the TX DMA meets the CPU's tx_desc[0] → suspended, TPS0 = 6).
WhyThe baseline case: proves that writing 1 clears, and that the test's starting state is 0.
Watch forIf TBU does not go back to 0 after clearing, the DMA may have touched a descriptor again right away (it does not without a new tail). Look at TPS0.

B: One frame, IOC = 0 in both directions status

Setupeth_tx_ioc = 0, eth_rx_ioc = 0 (default). Prints FLOW [10]/[11].
EventSend 60 bytes, receive them back, wait 200 µs.
Expected (DMACSR and more)1 = [TBU ETI ERI], 0 = [TI RI RBU AIS NIS]. DMAISR.DC0IS also printed.
WhyETI: the frame has entered the MTL TX FIFO; ERI: the DMA has written the first RX buffer; TBU: sending done, the DMA met the CPU's descriptor again. No TI/RI because the descriptors did not request it (IOC = 0). AIS/NIS = 0 because DMACIER = 0 (p.3094).
Watch forThe mode 4 log (11-07) already gave exactly 0x2C04 = TBU ETI ERI (+CDE) with AIS = 0. Mode 12 repeats it on purpose.

C: One frame, IOC = 1 in both directions status

Setupeth_tx_ioc = 1 (TDES2.IOC [31]), eth_rx_ioc = 1 (RDES3.IOC [30] on every descriptor handed back from now on).
Event8 warm-up frames to turn the RX ring all the way round (the old descriptors have no IOC, and the DMA already holds the next one), clear, then the 9th frame is graded.
Expected (DMACSR and more)1 = [TI RI TBU ETI ERI], 0 = [AIS NIS].
WhyTI/RI only come up when the descriptor has IOC (p.3050, p.3064). Still no NIS even though TI/RI belong to the normal group: enable = 0.
Watch forAfter C, eth_rx_ioc stays 1, so RI still comes up in later cases (not graded). Lesson: do not modify a descriptor the DMA is holding; turn the ring instead.

D: Write-1-to-clear, bit by bit status

SetupThe state left over from C (TI RI TBU ETI ERI = 1).
EventWrite DMACSR = TI → read; write 0 → read; write every bit → read.
Expected (DMACSR and more)After writing TI: TI = 0, the other bits unchanged. After writing 0: no change. After writing all: 0.
WhyAccess column on p.3094: rc_w1. Writing 0 is harmless, so a driver can write back exactly the value it just read to clear "everything it has seen".
Watch forThis is the standard way to clear in an ISR: v = DMACSR; DMACSR = v;. If D is BAD, that way of clearing is wrong.

E: RX out of descriptors: RBU, a frame waits in the FIFO status

SetupRX ring of 8 descriptors. Read MTLRXQMPOCR and DMACMFCR first so the (clear-on-read) counters start at 0.
EventSend 9 frames of 60 bytes without reading any. Then read MTLRXQDR.PRXQ, MTLRXQMPOCR, DMACMFCR; after that read the 9 frames.
Expected (DMACSR and more)1 = [RBU], 0 = [AIS NIS FBE]; RPS0 = 4 (suspended); PRXQ = 1; missed = overflow = 0; DMACMFCR = 0; 9/9 read back identical; afterwards RPS0 = 3.
WhyFrame 9 has no room: the DMA suspends, but the MTL FIFO still has space, so it holds the frame and nothing is lost. The first give-back writes the RX tail → the DMA wakes up, and frame 9 goes into rx_desc[0].
Watch forRBU is "abnormal" but not a data error: the driver only needs to supply descriptors + write the tail. AIS is still 0.

F: RX FIFO overflow: RXOVFIS status

SetupAs in E. RX FIFO 2048 bytes (RQS = 7). RSF = 0.
EventSend 10 frames of 1514 bytes without reading. 8 go into the ring, frame 9 (1518 bytes with FCS) sits in the FIFO, frame 10 has no room left.
Expected (DMACSR and more)1 = [RBU]; ETH_MTLQICSR.RXOVFIS = 1; MTLRXQMPOCR overflow ≥ 1; 9/10 read back. Also prints MTLISR.Q0IS and DMAISR.MTLIS (not known yet whether they come up with nothing enabled).
WhyOverflow is an MTL event, not a DMA event: it lives in MTLQICSR (rc_w1), with the counter in MTLRXQMPOCR (clear on read).
Watch forIf a frame arrives with RDES3.OE = 1, the MTL has forwarded a truncated frame (p.3105). After the case: write 1 to RXOVFIS, print again.

G: Watchdog RX: RWT status

SetupETH_MACWTR = PWE | WTO = 0 (2 KB) (p.3120); ETH_MACCR JE = 1, WD = 0 so TX can send 2100 bytes.
EventSend 2100 bytes. The receiver cuts at 2048.
Expected (DMACSR and more)ingress returns −3 (ES); RDES3 RWT [22] = 1; 1 = [RWT]; ETH_MACRXTXSR.RWT [8] = 1 (read last, read to clear); MACISR.RXSTSIS also printed. Afterwards: write 1 to RWT, then write 0, to find out whether it is rc_w1 or rw.
WhyRWT goes through three layers: the descriptor (bad frame), DMACSR bit 9, MAC status. The access column for bit 9 says "rw", unlike every other bit: the code tries both ways of clearing and prints which one works.
Watch forEnd of case: MACWTR = 0, eth_rx_flush. 0x200 is not in the common clear mask IS_DMACSR_W1C because it is not yet known whether it is rw or rc_w1.

H1: Stopping the TX DMA: ST = 0 status

SetupETH_DMACTXCR.ST [0] (p.3079).
EventST = 0, wait 200 µs, read; ST = 1 again; send a frame.
Expected (DMACSR and more)1 = [TPS]; TPS0 = 0 (stopped); the frame sent after restarting comes back SAME.
WhyTPS = "Transmit Process Stopped", abnormal group, set when the DMA stops on command. Not an error.
Watch forStopping/restarting the DMA is what a driver does when it changes configuration (RM §61.9.1). H1 shows that doing so does not lose the ring.

H2: Stopping the RX DMA: SR = 0 status

SetupETH_DMACRXCR.SR [0] (p.3081).
EventSR = 0, wait, read; SR = 1; one frame.
Expected (DMACSR and more)1 = [RPS]; RPS0 = 0; the frame comes back SAME.
WhyRPS is bit 8; like H1 but for the receiver.
Watch forAfter SR = 1 the DMA continues from the current descriptor; the ring is not scrambled.

I: Bus error: TX buffer in DTCM BAD-case

SetupHand-built descriptor: TDES0 = 0x20000000 (DTCM), B1L = FL = 60, OWN | FD | LD; write the TX tail. Last case.
EventThe Ethernet DMA cannot reach DTCM (RM §2.1.7 p.113: only the CPU and MDMA) → AHB returns an error.
Expected (DMACSR and more)1 = [FBE TPS], 0 = [AIS NIS]; TEB: bit 0 = 1 (read), bit 1 = 0 (data buffer, not descriptor), bit 2 printed; TPS0 = 0; TDES3 still has OWN = 1 (the DMA does not close it).
Whyp.3095: when FBE = 1 the DMA channel shuts off all bus access. Only a software reset (eth_reset_mac in the next test) recovers it. This is the classic STM32H7 mistake: putting Ethernet buffers in DTCM/ITCM.
Watch forIf the board does not raise FBE within 10 ms: DTCM may be readable over AHB on this silicon (a surprise, worth recording). The meaning of TEB bit 2 for a buffer error is not clear yet.
