PTP timestamp: the MAC stamps the time on frames (mode 3)

Cheat sheet for eth_run_test_ops = 3 (eth_mac_ptp_lb, file eth_ptp_functions.c). STM32H755, RM0399 Rev 4. The two-step part ran on the board on 2026-11-06 (7/7); the one-step part was written later and has no log in the repo yet.

Mnemonic: The MAC has its own clock (system time). With TTSE set, when the frame's SFD passes the MII the MAC copies the time into TDES0/1; with TSENALL set, every received frame is followed by a context descriptor holding the time. One-step: add an OSTC context before the Sync, and the MAC fills the time into bytes 48..57 of the frame by itself.

1. What mode 3 tests

IEEE 1588 (PTP) synchronises clocks between machines by recording exactly when a frame leaves and arrives. Software cannot do this accurately enough (interrupts, cache, queues), so the MAC has a timestamp block (RM0399 §61.5, programming guide §61.9.9 p.3036): a time counter driven by the PTP clock (= HCLK on the H755, p.2936) and a capture circuit right at the MII. Mode 3 only asks the hardware three questions: is the counter running, are the TX and RX times written into the descriptors, and are those two times consistent with each other. No PTP protocol, no conversion to ns.

Part two (added after the 11-06 log): one-step. With two-step, the master sends Sync and then has to send a Follow_Up carrying the time read from TDES0/1. With one-step the MAC fills the time straight into the Sync as it goes out (p.2983-2985), and the CPU no longer sends Follow_Up. The test sends an OSTC context descriptor, then a Sync with originTimestamp = 0, and looks at bytes 48..57 of the returned frame.

Three things mode 3 deliberately keeps simple: coarse update (SSINC added directly every tick), SSINC = 1 (sub-second is a raw tick count), binary rollover (seconds only step after 2³¹ ticks). So every printed value is a count of HCLK ticks, not real seconds/nanoseconds; section 10 explains how a real driver does it.

Order matters: write STSUR/STNUR first, then set TSINIT; and wait for TSINIT to self-clear before writing ETH_MACTSCR again (the code waits at most 1000 µs; on timeout it returns 0 and the mode FAILs). Writing TSENALL together with TSINIT also works, but the code splits them so FLOW is easier to read.

Reading the time (ptp_read_time): seconds, sub-second, then seconds again; if the two seconds reads differ, read again (p.3180). The read is not atomic, so without this the time can be wrong by exactly one second.

Sequence in ingress_packet_status: the frame arrives in rx_desc[n] → copy, hand the descriptor back to the DMA → if eth_ptp_on and RDES3.LD, RS1V and RDES1.TSA = 1, call ingress_context: wait for rx_desc[n+1] to have OWN = 0 and CTXT = 1, copy RDES0/1 into eth_rx_ts, hand that descriptor back too. If it meets CTXT while PTP is off, ingress_packet_status returns −4 (not a frame).

TSENALL = 1 means every frame costs two RX descriptors. A ring of 8 descriptors can only hold 4 unread frames. A real driver enables TSIPENA + TSEVNTENA so only PTP frames get a context (section 10, P4).

4. Sync frame and master mode (one-step)

60-byte Sync frame (PTP over Ethernet, IEEE 1588-2008), sent with originTimestamp = 0:
  [ 0.. 5] DA  6C 1F F7 CA 2B FD        [ 6..11] SA  00 80 E1 00 00 00
  [12..13] EtherType       88 F7        PTP over Ethernet (TSIPENA)
  [14]     messageType     00           transportSpecific 0, Sync = 0
  [15]     versionPTP      02           TSVER2ENA
  [16..17] messageLength   00 2C        44-byte header + originTimestamp
  [18]     domainNumber    00
  [20..21] flagField       00 00        bit 1 of byte 20 twoStepFlag = 0: one-step
  [22..29] correctionField 00 x 8       the MAC may touch it (Table 564: "subnanosecond correction")
  [34..43] sourcePortIdentity  SA + 00 01   clockIdentity + port 1
  [44..45] sequenceId      00 01 / 00 02
  [46]     controlField    00           Sync
  [47]     logMessageInterval 00
  [48..53] originTimestamp seconds (48 bit)       <- written by the MAC with OSTC
  [54..57] originTimestamp nanoseconds (32 bit)  <- written by the MAC with OSTC
  [58..59] pad

So the MAC recognises this as a Sync that needs its time filled in, ptp_one_step adds these bits to ETH_MACTSCR (value after the write: 0x0000CD01):

BitValueWhyRM
TSVER2ENA [10]1PTP version 2 headerp.3177
TSIPENA [11]1recognise PTP over Ethernet (EtherType 0x88F7); PTP over UDP needs TSIPV4ENA/TSIPV6ENAp.3177
TSEVNTENA [14]1event messages only (Sync, Delay_Req, Pdelay_*), not general messagesp.3177

Table 564 p.2983 is the lookup table: the SNAPTYPSEL / TSMSTRENA / TSEVNTENA columns tell which message gets captured. 00 / 1 / 1 = master, event: Sync. Changing TSMSTRENA = 0 makes it a slave: Delay_Req. SNAPTYPSEL = 01 captures every event message, 10 adds Pdelay.
