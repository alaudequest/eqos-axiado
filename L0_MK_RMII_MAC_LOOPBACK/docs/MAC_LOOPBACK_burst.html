DMA burst: mode 2, each setting, each length

Cheat sheet for eth_run_test_ops = 2 (eth_mac_burst_lb, file eth_burst_functions.c). STM32H755, RM0399 Rev 4, Synopsys DWC EQoS databook 5.50a. Mode 2 has no board log in the repo yet (folder CM7/Core/Src/log has no "DMA BURST TEST" table): every "after" number below is what the databook predicts; section 7 is waiting for a log. Q&A-style questions about FB / AAL / PBL are already on the Q&A page; this page follows exactly the order in which the code runs.

Mnemonic: The DMA does not copy byte by byte; it copies 4-byte beats grouped into bursts. FB = 1 forces a burst to be 1, 4, 8 or 16 beats; AAL = 1 forces a burst to start at an address divisible by the burst size. When a frame ends in the middle of a burst, the DMA either shrinks the burst or writes dummy beats: mode 2 fills the buffer with AA to see which one it picks.

1. What mode 2 tests

Every other mode only asks "does the frame come back intact". Mode 2 also asks: how many bytes did the DMA write into RAM for a frame that is len bytes long? In theory exactly PL bytes (RDES3.PL, frame length without FCS). In practice the DMA writes over the 32-bit AHB bus in bursts, and how bursts are formed is decided by ETH_DMASBMR (p.3076): with fixed bursts (FB = 1) the databook says the DMA may write a few extra "dummy" beats to round off the burst (§2.2.1.5, figure 2-11). Those dummy bytes sit after the frame in the buffer; they do not harm the data, but they are the only trace of the burst that software can see.

How it is measured: before each frame, fill the buffer with 0xAA (the frame payload never uses this value), send, receive, then scan from PL to the end of the buffer for the last byte that is not AA. That distance is the after column.

Loopback inside the MAC gives no view of the bus: no logic analyser, no burst counter. The test can only prove two things: (1) the data comes back correct in all 4 modes, (2) whether or not the DMA writes extra bytes after PL. It does not measure speed, does not see how long the real bursts are, and does not see the AHB 1 KB boundary. Conclusions about FB/AAL performance must come from the databook, not from this mode.

2. ETH_DMASBMR: FB and AAL (p.3076)

BitNameProject valueMeaning
[0]FB Fixed Burst Length11: the DMA only uses SINGLE, INCR4, INCR8, INCR16 bursts (and never more than PBL). 0: the DMA uses INCR of any length ("undefined length"), stopping when the data runs out
[12]AAL Address-Aligned Beats11: every burst starts at an address divisible by the burst size (INCR16 → address divisible by 64). Only meaningful with FB = 1 or with an AXI bus; with FB = 0 the DMA still aligns the first beat (databook §2.2.1.3)
[14]MB Mixed Burstreads 0Allows mixing fixed bursts and INCR. RM0399 marks it reserved/0 on the H755: mode "FB=0" is pure INCR
[15]RB Rebuild INCRx Burst0When the bus splits a burst, the DMA rebuilds it as INCRx. Not touched in the test

The four burst types on AHB, by size:

BurstBeats × 4 bytesWhen the DMA uses it
SINGLE1 × 4 = 41 beat left at the tail, or FB = 1 with the address not aligned yet
INCR4 / INCR8 / INCR164 / 8 / 16 beat = 16 / 32 / 64 byteFB = 1: the largest size ≤ PBL and ≤ the remaining data (and address-aligned if AAL = 1)
INCR (undefined)any, at most PBL beatsFB = 0: one burst up to PBL or until the data runs out

PBL is not in DMASBMR: TXPBL is in ETH_DMACTXCR [21:16] (p.3079), RXPBL in ETH_DMACRXCR [21:16] (p.3081), and ETH_DMACCR.PBLX8 [16] (p.3078) multiplies both by 8. The project sets 8 × 8 = 64 beats = 256 bytes per DMA bus request. That is why the length table has 255 / 256 / 257.

Write order matters: mac_dma_init() writes ETH_DMASBMR while the DMA is still stopped (ST = SR = 0), following RM §61.9.1 p.3031 (bus mode first, descriptors next, ST/SR last). That is why mode 2 resets + re-inits for each mode instead of overwriting DMASBMR on the fly.

The last two lines of Summary are automatic conclusions: FB=0 "OK" when no FB = 0 mode has after ≥ 4; FB=1 "placeholder beats after N frame(s)" when at least one such frame exists, otherwise "no placeholder beat … exact INCRx/SINGLE".

6. The four modes, one at a time

Labelled "assumed" because there is no log yet. Each card gives what the databook predicts and how to read it if the board says otherwise.

M1: FB = 1, AAL = 1 (driver default) assumed

ETH_DMASBMR0x00001001: FB [0] = 1, AAL [12] = 1
Bursts the DMA usesonly SINGLE / INCR4 / INCR8 / INCR16; every burst starts at an address divisible by the burst size (AAL)
expected after0..3 if the DMA picks the right burst size for the tail (§2.3.1 p.81: "INCRx or SINGLE"); or up to the end of the unfinished beat/burst if the DMA fills in dummy beats (§2.2.1.5, figure 2-11)
WhyThe databook allows both: when the remaining data is less than a burst, the DMA either shrinks the burst size (INCR16 → INCR8 → INCR4 → SINGLE) or runs the whole burst with dummy beats. Only the board can tell which one the H755 picks.
Watch forThis is the configuration mac_dma_init() uses for every other mode (eth_functions.c p.3076 in the table). The project's buffers are at address 0x2400_53E0 + n × 2304: 32 mod 64, so with AAL = 1 the first INCR16 burst cannot start right at byte 0 of the buffer: the DMA has to use a smaller burst (INCR8 = 32 bytes) to reach the 64 boundary before running INCR16. The end%64 column shows where the frame ends inside a 64-byte block.
If it differs from what is expectedafter > 3 at a few lengths, with after + end%64 reaching a 16, 32 or 64 boundary → the DMA padded to round off an INCR4 / 8 / 16 burst. after > 3 at EVERY length, even 60 → re-check the scan (BT_FILL) before drawing conclusions.

M2: FB = 0, AAL = 1 assumed

ETH_DMASBMR0x00001000: FB [0] = 0, AAL [12] = 1
Bursts the DMA usesINCR of any length (undefined length); MB reads 0 on the H755 so there is no mixed burst; AAL still aligns the start address
expected after≤ 3 (the rest of the last 32-bit word)
WhyAn INCR burst ends exactly where the data runs out; no padding needed (§2.2.1.5). Only the last word may be over-written because the bus is 32 bits.
Watch forIf M1 gives after > 3 while M2 gives ≤ 3, that difference is the clearest evidence of FB. On the H755's internal AHB bus FB = 0 is usually slightly faster (fewer dummy beats), but ST recommends FB = 1 in the HAL; the project keeps FB = 1 to match the driver.
If it differs from what is expectedafter > 3 here disagrees with the databook: the code prints "FB=0: … differs from the databook". In that case suspect that ST's DMA does not honour FB = 0, or that something else writes into the buffer (cache! the D-cache must be off for this region, or invalidated).

M3: FB = 1, AAL = 0 assumed

ETH_DMASBMR0x00000001: FB [0] = 1, AAL [12] = 0
Bursts the DMA usesSINGLE / INCR4 / 8 / 16, but a burst may start at an address that is not aligned to the burst size
expected afterlike M1; may differ at lengths 61..63 and in the buffer's first frame
WhyWithout address alignment an INCR16 burst can start right at byte 0 of the buffer (0x…53E0): the burst boundaries shift by 32 bytes compared with M1, so the "padding" (if any) lands on different lengths.
Watch forCompare M3 with M1 length by length: the same after means AAL has no effect on the trace in RAM (it only changes how bursts are split on the bus). A different after: note which lengths differ; that is where the burst boundaries are.
If it differs from what is expectedDatabook §2.2.1.3: AAL = 0 can make a burst cross the AHB 1 KB boundary and get split by the bus. Not visible from RAM; noted only.

M4: FB = 0, AAL = 0 assumed

ETH_DMASBMR0x00000000: FB [0] = 0, AAL [12] = 0
Bursts the DMA usesINCR of any length, no address alignment: the "freest" configuration
expected after≤ 3, like M2
WhyFB = 0 decides after; AAL cannot change the number of bytes the DMA writes, because an INCR burst stops when the data runs out.
Watch forLast mode: the MAC stays in this configuration until another test calls eth_reset_mac() (comment at the top of eth_mac_burst_lb). Running mode 0 right after mode 2 is fine because mode 0 also resets.

7. Lessons from the board

There is no mode 2 log in the repo yet. When it runs, paste from the line DMA BURST TEST to Burst test finished. Things to look at first:

  1. Is data SAME 56/56? If not, stop there: bursts cannot corrupt data; the bug is elsewhere (cache, buffer, PL).
  2. Modes M2 / M4 (FB = 0): is after ≤ 3? Yes → ST's DMA honours FB = 0.
  3. Mode M1: what is the largest after, at which length, and which boundary (16, 32, 64) does after + end%64 reach → the burst size the DMA left unfinished.
  4. M1 vs M3 line by line: does AAL shift the boundaries?
  5. Pattern "after = 4 in every mode, at every length" → suspect the FCS, not bursts.
